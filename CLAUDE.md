# The Collective

macOS menu bar app that shows running coding agents and their subagents: the count in the icon, details (agent type, prompt, current tool, runtime) in the popover. Claude Code, Codex and Antigravity are supported; more tools come in through adapters.

Plan, state and decisions live in the GitHub issues of this repository.

## Layout

- `CollectiveKit/`: local Swift package with all the logic, no UI.
  - `Model/`: tool-neutral types (`SessionKey`, `AgentRef`, `AgentEvent`, `Session`, `Agent`)
  - `Store/CollectiveState.swift`: pure reducer `apply(event)`, plus `markStale` and `prune`
  - `Sources/`: adapter protocols (`PushAdapter` for hook payloads from subspace, e.g. Claude Code, Codex and Antigravity; `PullSource` for watching files of its own) and one adapter per tool. Every `PushAdapter` names its spool folder (`spoolRoot`; a tool with several data folders, such as Antigravity's CLI and Desktop App, names several in `spoolRoots`)
  - `Spool/`: `SpoolReader` reads the subspace folders of all adapters (FSEvents, existing files at launch) and dispatches the envelopes by `source`; it keeps the mapped events in the `EventStore` from `SubspaceKit` (SQLite in the app's Application Support) and replays them at launch
  - `Theme/`: base16/base24 schemes and roles as in Unimatrix Zero. `CollectiveUI` keeps the theme in the environment (`\.theme`, `.role(_:)`), plus IBM Plex (`Font.plexSans`, `Font.plexMono`) and Lucide (`LucideImage`) as bundled resources. All 38 Unimatrix schemes are bundled byte-equal (`Resources/Schemes/`, 14 families), names from `ThemeFamily` (`Theme.family`/`shortName`/`displayName`), derived only when needed (`ThemeShelf`). Custom themes: `CustomThemeFolder` reads `~/Library/Application Support/The Collective/Themes/`, `CustomThemeLibrary` watches the folder, `ThemeCatalog` merges bundled and custom ones; the live catalog lives in the app in `ThemeCatalogStore`.
  - `Presentation/` and `Resources/`: models of the windows. The scheme choice per appearance (Settings › Appearance) lives in `Presentation/AppearanceModel.swift` (`ThemeChoice`, resolution and fallback in `ThemeResolution.swift`, pane model with `AppearanceKeyboard`, `AppearanceListLayout` and `CustomThemeImportAlert`); the license texts for About are generated by `scripts/acknowledgements.sh` (license per family from `CollectiveKit/Acknowledgements/`) as the checked-in resource `Resources/Acknowledgements.json` (model `Presentation/Acknowledgements.swift`)
  - From the package `SubspaceKit` (`SubspaceKit/`): mapping interpreter and loader with the bundled mapping documents (`Sources/SubspaceKit/Mapping/`, `Sources/SubspaceKit/Resources/Mappings/`), plus `EventStore` and the spool building blocks (`SpoolScanner`, `SpoolFile`, `SubspaceRoot`, `FSEventsWatcher`) and `SourceID`/`Envelope`
- `SubspaceKit/`: separate local Swift package (target and product `SubspaceKit`), the reader for subspace: spool (`Envelope`, `SpoolFile`, `SpoolScanner`, `SubspaceRoot`, `FSEventsWatcher`), mapping (`JSONValue`, `JSONPointer`, `MappingDocument`, `MappingInterpreter`, `MappingLoader`, bundled mapping documents) and `EventStore`. Scope: everything up to and including `MappingResult`; what an app makes of the events (adapters, `AgentEvent`, reducer, UI) belongs in `CollectiveKit`. It stays a package of its own so it can be split out again for a second Swift host. Rules:
  - App- and source-neutral: sources are open strings (`SourceID`), the code names neither The Collective nor any other app
  - Mapping conformance: the interpreter follows subspace `docs/model.md` §5.1 like `apply.py`; where they could differ, `apply.py` is right (comparison by code points, integers of any size), intended differences are commented. `MappingConformanceTests` run against the golden files in the subspace checkout and stay at 0 mismatches
  - Reads only `$ROOT` (contract §3, §6); the store lives in the app's Application Support, the app passes the path
  - No SwiftUI import: no UI, no app logic
  - Tests only against captured payloads (`SubspaceKit/Tests/SubspaceKitTests/Fixtures/`, subspace `fixtures/`) or the golden files under subspace `tools/model/`, never against made-up formats
  - Dependencies only GRDB and yyjson; `public` only what the app needs, documented with `///`
  - Tests: `cd SubspaceKit && swift test`, after a change also the tests of `CollectiveKit`
- `App/`: Xcode project `Collective` (macOS 15, no App Sandbox, `LSUIElement`), links `CollectiveKit` and `SubspaceKit` locally. Stays thin: `MenuBarExtra`, `CollectiveModel` starts the `SpoolReader`. App updates come from Sparkle 2 (`SparkleUpdater`, the only code that imports it); it reports into the kit's tool-neutral `AppUpdateState`. `App/Info.plist` holds only the Sparkle keys, the rest of the Info.plist is generated from the build settings. Synchronized folders, new files need no change to `project.pbxproj`. `App/Version.xcconfig` is the single source of the version (base configuration for Debug and Release). Project settings (deployment target, signing, capabilities) are the maintainer's call.
- `Design/icons/`: template icons as SVG (menu bar idle and warning; `menubar-working.svg` is only a design source and no longer rendered); `render-menubar.sh` turns them into the template PNGs in the asset catalog (needs `rsvg-convert`). The colored cube of the menu bar (working, waiting for approval) is drawn by the app at runtime (`MenuBarSceneImage` in `CollectiveUI`).

The hooks are **not here** but in subspace ([`we-are-the-borg/subspace`](https://github.com/we-are-the-borg/subspace)), expected as a sibling checkout at `../../we-are-the-borg/subspace` (or `$SUBSPACE_DEV_DIR`). It holds the contract (`docs/contract.md`: spool path, envelope, consumer duties, mapping in §12; plus `docs/model.md`), the hook capture and the fixtures. This app is the consumer `agent-collective` there. Contract and mapping issues belong in subspace.

## Architecture rules

- **Extensibility:** model, store and UI know only tool-neutral types. Anything tool-specific lives in an adapter only. A new tool = a new adapter plus its registration, without changes to model, store or UI. If that needs a change to the core, question the core design first.
- The source is an open string (`SourceID`), **not an enum**.
- Adapters are tested against **real, captured payloads**, not against guessed formats.
- **Mapping rule:** adapters read payloads only through the subspace mapping (target fields: core plus source block, `$ROOT/model/<source>.json`, bundled copy in `SubspaceKit/Sources/SubspaceKit/Resources/Mappings/`, interpreter and loader in `SubspaceKit/Sources/SubspaceKit/Mapping/`). No raw payload paths in an adapter. If a target field is missing, request it in subspace (a mapping change there), don't read it from `payload` in the adapter. Exceptions: side files the mapping doesn't cover (Claude Code `meta.json`, the first line `session_meta` of the Codex rollout, contract §8, and the `turn_context` entries of the Codex rollout, who answers an approval and with which effort the turn runs, contract §6, `docs/model.md` §4.3, and the first record of an Antigravity child conversation's transcript at `transcript_path` to link a subagent conversation to its parent, contract §8), the effort derived from a known suffix of the Antigravity target field `model` until subspace has an `effort` target field for it, and the one-line tool detail from the opaque `tool_input` (allowed in subspace `docs/model.md` §9). subspace delivers the command as the target field `command`; the exception covers only the other keys (`pattern`, `url`, `query`, `description`, `path`).
- **Roles only:** everything the app draws itself takes its color from a theme role (`.role(…)` or `@Environment(\.theme)`), never a fixed color or a system color (`.primary`, `.secondary`, `accentColor`, `Color.white`, materials). Fonts are IBM Plex Sans and Plex Mono (`Font.plexSans`, `Font.plexMono`), symbols are Lucide (`LucideImage`), no SF Symbols. The only exceptions are what the system draws: notifications, menus, context menus, dialogs and the menu bar itself. If a role is missing, it is requested in Unimatrix Zero, not invented here.
- Transport is the subspace spool, not a socket. Changes to the envelope belong in the subspace contract, not here as a special case.
- **Sessions, not folders:** The Collective shows agent sessions. Repository data (pull requests, CI, `gh`) stays out.

## Commands

```sh
(cd CollectiveKit && swift test)   # Swift Testing (import Testing)
(cd SubspaceKit && swift test)     # SubspaceKit, conformance against the subspace checkout
xcodebuild -project App/Collective.xcodeproj -scheme Collective -configuration Debug CODE_SIGNING_ALLOWED=NO build
scripts/public-check.sh            # no private data in tracked files (README › Checking for private data)
scripts/release.sh prepare|publish # release (README › Releasing)
```

## Workflow

- Never commit directly to `main`: branch → PR → squash merge.
- Agents never commit or push: the maintainer does. Agents end with a proposed PR title and body.
- PR titles follow Conventional Commits (types `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `chore`; scopes e.g. `popover`, `menubar`, `notifications`, `settings`, `setup`, `spool`, `kit`, `claude-code`, `codex`, `antigravity`), because the squash commit on `main` decides version and changelog (git-cliff, `cliff.toml`).
- Release: `scripts/release.sh prepare` → PR `chore(release): vX.Y.Z` (squash merge) → `scripts/release.sh publish` on `main`. Notarizing and publishing are done by the maintainer.
- Everything in the repository is English: code, comments, commits, README, issues.
- Captures of sessions with subagents (`claude -p` …) are started by the maintainer (see subspace `tools/hook-capture/`).
